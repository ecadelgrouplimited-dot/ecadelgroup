Chapter One

Server Overview

Before managing a VPS you must understand what it is, what is running on it, and how all the pieces connect. This chapter gives the full picture of our production server.

What is a VPS?

A Virtual Private Server (VPS) is a dedicated slice of a physical server, with guaranteed CPU, RAM, and disk allocated exclusively to us. Unlike shared hosting, we have full root access — meaning we can install anything, configure everything, and take full responsibility for security and uptime.

Our VPS runs Ubuntu 24.04 LTS — a Linux operating system. Everything we do is through the Linux command line.

Chapter Two

Accessing the Server

SSH (Secure Shell) is the encrypted tunnel through which all server management happens. Understanding it is the foundation of everything else in this guide.

⚠ Security Rule

The server uses key-based SSH only. Password authentication has been disabled. Never share your private key. If a key is compromised, remove it from the server immediately.

Method 1 — SSH from Terminal (Primary Method)

This requires your SSH private key to be set up on your machine. Team members must have their public key added to the server by an administrator first.

Terminal — connect to server 
ssh root@72.62.185.212

# If you have multiple SSH keys, specify the correct one:
ssh -i ~/.ssh/your_private_key root@72.62.185.212

# For the lead developer (ECADEL key configured):
ssh root@72.62.185.212  # uses ~/.ssh/ecadelgroup_github automatically

Method 2 — Hostinger Browser Terminal (Backup Method)

Always available via the Hostinger hPanel even when SSH is unavailable. Go to: hpanel.hostinger.com → VPS → srv1713793.hstgr.cloud → Terminal button. This bypasses SSH entirely and connects directly through Hostinger's infrastructure.

ℹ When to use the browser terminal

Use Hostinger's terminal when: SSH is not responding, the server is under a load attack, you are locked out, or you are away from your usual machine and don't have your SSH key.

Adding a New Team Member's SSH Key

Every team member who needs server access must generate their own SSH key pair. They give you their public key only. You add it to the server. They keep their private key secret.

01

Team member generates a key pair on their machine

# Press Enter for default location (~/.ssh/id_ed25519)
# Set a passphrase for extra security

02

You add their public key to the server

# SSH into the server, then:
echo "ssh-ed25519 AAAA...their_key... their@email.com" >> /root/.ssh/authorized_keys
cat /root/.ssh/authorized_keys  # Verify it's there
03

They test the connection

ssh root@72.62.185.212
# Expected: Welcome to Ubuntu 24.04 LTS...
04

Removing access (when someone leaves)

nano /root/.ssh/authorized_keys
# Delete the line containing their key, save (Ctrl+O, Ctrl+X)

Chapter Three

PM2 — Process Manager

PM2 is the software that keeps our Next.js applications running. Without PM2, if the app crashed or the server rebooted, the website would go offline and stay offline until someone manually restarted it. PM2 prevents that.

Understanding PM2

Think of PM2 as a supervisor. It watches our Next.js application at all times. If it crashes, PM2 restarts it automatically. When the server reboots, PM2 starts all saved processes automatically. It also collects logs so we can see what happened and when.

Checking the Status of All Applications

Check PM2 status 
pm2 status

# You should see something like:
┌─────┬──────────────┬─────────┬──────────┬────────┬──────┬───────────┐
│ id  │ name         │ mode    │ pid      │ uptime │ ↺    │ status    │
├─────┼──────────────┼─────────┼──────────┼────────┼──────┼───────────┤
│ 0   │ ecadelgroup  │ fork    │ 1422     │ 6h     │ 0    │ online    │
└─────┴──────────────┴─────────┴──────────┴────────┴──────┴───────────┘

# Status should be "online". Restart count (↺) should be 0 or low.
# High restart count means the app is crashing repeatedly.

Chapter Four

Nginx — Web Server

Nginx is the public-facing web server. It receives all incoming traffic on ports 80 and 443, handles SSL, and routes each domain to the correct Next.js application running on the server.

How Nginx Routing Works

Nginx uses configuration files called server blocks — one per domain. Each file lives in /etc/nginx/sites-available/ and is "enabled" by creating a symlink in /etc/nginx/sites-enabled/.

Common Nginx Commands

CommandWhat It Does
nginx -tTest configuration for syntax errors — ALWAYS run before reload
systemctl reload nginxReload config without dropping connections (preferred)
systemctl restart nginxFull restart — briefly drops connections
systemctl status nginxCheck if Nginx is running and see recent log lines
systemctl stop nginxStop Nginx (site goes offline)
systemctl start nginxStart Nginx
systemctl enable nginxMake Nginx start automatically on server boot

The ecadelgroup.com Configuration

/etc/nginx/sites-available/ecadelgroup.com 
# HTTP — redirect everything to HTTPS
server {
    listen 80;
    server_name ecadelgroup.com www.ecadelgroup.com;
    return 301 https://$host$request_uri;  # certbot added this
}

# HTTPS — serve the actual site
server {
    listen 443 ssl;
    server_name ecadelgroup.com www.ecadelgroup.com;

    # SSL certificates (managed by certbot)
    ssl_certificate     /etc/letsencrypt/live/ecadelgroup.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ecadelgroup.com/privkey.pem;

    # Proxy all requests to the Next.js app
    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

New project Nginx template (port 3001) 
server {
    listen 80;
    server_name newdomain.com www.newdomain.com;

    gzip on;
    gzip_types text/plain text/css application/json application/javascript;

    location / {
        proxy_pass http://localhost:3001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }
}

Chapter Six

SSL Certificates & HTTPS

SSL certificates encrypt the connection between the visitor's browser and our server. Without a valid certificate, browsers show a "Not Secure" warning. Our certificates are issued by Let's Encrypt and renew automatically.

How Let's Encrypt Works

Let's Encrypt is a free, automated certificate authority. It issues certificates valid for 90 days and sets up a scheduled task (cron job) to renew them automatically at around 60 days. You should never need to manually renew unless something goes wrong.

Checking Certificate Status

SSL certificate management 
# List all certificates and their expiry dates
certbot certificates
Found the following certs:
  Certificate Name: ecadelgroup.com
    Domains: ecadelgroup.com www.ecadelgroup.com
    Expiry Date: 2026-08-27 08:23:46+00:00 (VALID: 89 days)
    Certificate Path: /etc/letsencrypt/live/ecadelgroup.com/fullchain.pem

# Test the auto-renewal process (doesn't actually renew)
certbot renew --dry-run

# Force manual renewal (only if within 30 days of expiry or expired)
certbot renew
systemctl reload nginx

# Check when auto-renewal is scheduled
systemctl status certbot.timer

Getting a Certificate for a New Domain

Issue certificate for a new domain 
# Prerequisites: DNS must already point to 72.62.185.212 AND
# Nginx must be configured for the domain BEFORE running this
certbot --nginx \
  -d newdomain.com \
  -d www.newdomain.com \
  --non-interactive \
  --agree-tos \
  -m ecadel@ecadelgroup.com \
  --redirect

# --redirect automatically adds HTTP→HTTPS redirect to Nginx config
⚠ DNS Must Point to the VPS First

Before running certbot, the domain's A record must already be pointing to 72.62.185.212. Let's Encrypt verifies domain ownership by making an HTTP request to the domain — if DNS hasn't propagated, the certificate request will fail.

Chapter Seven

Security & Hardening

A VPS exposed to the internet is probed constantly by automated bots. This chapter covers the security layers we have in place, what each one does, and how to manage them.

⚠ Incident History — May 2026

Our server was compromised by a cryptocurrency miner (XMRig) via a leaked root password. This consumed 379% CPU and took the site offline. All sections in this chapter describe protections we put in place as a direct result. Never share passwords in chat applications or documents.

Security Layer 1 — UFW Firewall

UFW (Uncomplicated Firewall) blocks all incoming traffic by default except for the three ports our services legitimately need. Anything else — including any port a malicious process might try to open — is automatically rejected.

UFW management 
# Check current firewall rules
ufw status verbose
Status: active
To                         Action      From
--                         ------      ----
22/tcp                     ALLOW IN    Anywhere   (SSH)
80/tcp                     ALLOW IN    Anywhere   (HTTP)
443/tcp                    ALLOW IN    Anywhere   (HTTPS)

# Allow a new port (e.g., when adding a new service)
ufw allow 8080/tcp

# Block a port
ufw deny 8080/tcp

# Block a specific IP permanently
ufw deny from 192.168.1.100

# Check recent UFW activity in system logs
grep "UFW BLOCK" /var/log/syslog | tail -20

Security Layer 2 — Fail2ban

Fail2ban monitors SSH login attempts. After 3 failed attempts within 10 minutes, it bans the offending IP address for 24 hours. This defeats brute-force attacks that try millions of password combinations.

Fail2ban management 
# Check current bans
fail2ban-client status sshd
Status for the jail: sshd
|- Filter:  Currently banned: 3
|  `- Banned IP list: 185.220.101.45 92.63.197.48 194.165.16.72

# Unban a specific IP (e.g., if you locked yourself out)
fail2ban-client set sshd unbanip 185.220.101.45

# Check fail2ban service is running
systemctl status fail2ban

# View your configuration
cat /etc/fail2ban/jail.local

# Restart fail2ban after config changes
systemctl restart fail2ban

Security Layer 3 — SSH Key Authentication

Password-based SSH login is permanently disabled. Only those with an authorized SSH private key can log in. This means even if someone knows our server's IP and username, they cannot gain access without the key file.

Verify SSH hardening is in place 
grep -E "PasswordAuthentication|PermitRootLogin" /etc/ssh/sshd_config
PasswordAuthentication no
PermitRootLogin prohibit-password
# "no" and "prohibit-password" are the correct secure values

# View who is authorized to log in
cat /root/.ssh/authorized_keys

Hostinger's MonarX agent scans the server continuously for known malware signatures, PHP shells, cryptocurrency miners, and suspicious file modifications. It reports findings to the Hostinger hPanel.

Responding to a Security Incident

If the server shows signs of compromise (high CPU from unknown processes, unexpected outbound traffic, files you didn't create), act immediately in this order:

01

Identify the malicious processes

ps aux --sort=-%cpu | head -20
# Look for processes you don't recognise at the top
02

Kill malicious processes

kill -9 [PID]
# Or by name:
pkill -9 -f processname
03

Find and delete malware files

find /tmp /var/tmp /root /dev/shm -type f 2>/dev/null | grep -v proc
rm -rf /tmp/suspicious* /var/tmp/suspicious*
04

Check for persistence (cron jobs, startup scripts)

crontab -l
cat /root/.bashrc | tail -20
ls /etc/cron.d/ /etc/cron.daily/
05

Change all passwords and rotate SSH keys immediately

passwd root
# Review and remove any unfamiliar keys:
nano /root/.ssh/authorized_keys
06

Restore the site and run a full malware scan

pm2 restart ecadelgroup
systemctl restart monarx-agent
# Then check the Hostinger panel for scan results

Emergency Procedures

Site is Down
1. SSH in or use Hostinger terminal
2. pm2 restart ecadelgroup
3. If that fails: pm2 logs ecadelgroup
4. Check CPU: ps aux --sort=-%cpu | head -5
5. If miner detected: pkill -9 -f xmrig
Can't SSH In
1. Use Hostinger browser terminal (always works)
2. Check if fail2ban banned you: fail2ban-client status sshd
3. Unban your IP: fail2ban-client set sshd unbanip YOUR_IP
4. Verify your key: cat /root/.ssh/authorized_keys
Disk Full
1. Check: df -h
2. Clear PM2 logs: pm2 flush
3. Clear old nginx logs: logrotate -f /etc/logrotate.d/nginx
4. Find large files: du -sh /var/www/* /root/
Suspected Compromise
1. Kill unknown processes: pkill -9 -f [processname]
2. Change root password: passwd root
3. Review authorized keys: nano /root/.ssh/authorized_keys
4. Run malware scan via Hostinger panel
5. Report to team lead immediately

Team Rules — Non-Negotiable

⚠ Team Security Rules

1. Never share server passwords in chat, email, or documents. Use SSH keys instead.

2. Never disable the firewall to "test something" without re-enabling it immediately.

3. Never run random scripts from the internet with curl | bash without reading the script first.

4. Always run nginx -t before systemctl reload nginx. A failed test with a reload can take the site down.

5. Never delete files you don't recognise until you've confirmed what they are — they might be critical system files.

6. Always create a backup before making major configuration changes.
